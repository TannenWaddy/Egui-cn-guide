# 第三章 即时模式 GUI

理解 egui，必须先理解“即时模式（immediate mode）”。这是 egui 和传统 GUI 框架（Qt、GTK、WinForms、Web 前端）最根本的区别。

## 3.1 两种模式对比

### 保留模式（retained mode）

传统 GUI 一般是保留模式：

```text
1. 创建一个按钮对象
2. 把它加到某个容器里
3. 注册一个 on_click 回调
4. 之后想改按钮文字，得持有它的引用去改
```

按钮对象长期存在内存里，框架替你维护它的状态。

### 即时模式（immediate mode）

egui 是即时模式：

```rust
if ui.button("Save file").clicked() {
    save(file);
}
```

这行代码**每帧都执行**（一秒可能 60 次）。每次执行时：

1. egui 现场排版“Save file”几个字，算出按钮该多大。
2. 决定按钮放哪里。
3. 查鼠标是否在这个位置上、是否点击了。
4. 根据是否被悬停/点击选颜色。
5. 把按钮画出来（加到这一帧的绘制列表里）。
6. 返回一个 `Response`，告诉你“点没点”。

**按钮对象根本不存在**。这行代码跑完，按钮就消失了，只剩下一些画到屏幕上的像素和一个 `Response`。

## 3.2 谁来存状态

既然按钮不存在，那“滑块当前拖到哪了”“窗口当前在什么位置”这些状态存哪？

- **应用数据**：你自己存。比如 `age: u32`、`name: String` 放在你的 `App` 结构体里。
- **egui 内部状态**：比如窗口位置、滚动距离，egui 用一个 `Id` 当 key 帮你存。你只需要保证 `Id` 唯一。

看这段：

```rust
ui.add(egui::Slider::new(&mut value, 0.0..=100.0).text("My value"));
```

egui 读 `value` 来显示滑块位置，然后看鼠标有没有在拖滑块，如果有就把拖动量加到 `value` 上。**egui 不替你存 `value`**，你必须在帧之间保留它。

## 3.3 即时模式的好处

写起来简单，代码逻辑直：

- 不需要回调函数打断你的代码流。
- 不用担心某个回调触发时，它要操作的数据已经没了。
- GUI 代码可以就是个普通函数，不需要为了 UI 单独建个类。
- UI 永远显示最新状态——因为它每帧都根据你的数据重新画，不存在“数据变了 UI 没刷新”的问题。

简单说：**少了一堆样板代码，少了一堆因为状态不同步导致的 bug**。

## 3.4 即时模式的坏处

### （1）布局更难

假设你想在屏幕正中间显示一个对话框。要居中，egui 得先知道这个对话框多大；要知道多大，得先把里面的内容排一遍；可排内容时又要判断“OK 按钮被点了吗”，这又需要先知道窗口在哪……

这是个鸡生蛋问题。egui 的处理方式：

- 对“原子控件”（按钮、标签）——egui 在画之前就知道它多大，所以居中没问题。
- 对复杂容器（窗口、Grid）——egui 用**上一帧的尺寸**来定位，所以新出现的窗口可能第一帧位置不对，下一帧才纠正。这就是所谓的“first-frame jitter”。
- 对部分组件（如 `Grid`），egui 会用 `Context::request_discard` 触发**额外一帧（多 pass）**来纠正，让用户看不到那个抖动。多 pass 会多花 CPU，所以默认大多数帧还是单 pass。

### （2）CPU 占用

每帧都要把整个界面重新排一遍。如果你的界面特别复杂（比如一个超长的滚动列表），每帧排一遍可能吃不消。

应对：

- 滚动区只排可见的那部分（egui 的 `ScrollArea` 会做这件事）。
- 没有交互、没有动画时 egui 不会重绘，不浪费 CPU。
- 大多数情况下 egui 一帧占 1~2ms，不用担心。

反过来说：界面交互很重时，即时模式可能比保留模式还快。想想你拖浏览器窗口时它有多卡——那是保留模式在重新算布局。egui 拖窗口是丝滑 60 FPS。

### （3）ID 麻烦

有些状态 egui 必须自己存（窗口位置、滚动距离、哪个滑块在被拖）。这时 egui 需要一个**唯一 ID**当 key。

大部分时候 ID 是自动生成的（按位置和调用顺序），你不用管。但有些情况你得手动给 ID：

- 两个窗口同名——默认 egui 拿窗口标题当 ID，会冲突。
- 在循环里创建控件——同位置同顺序可能撞 ID。

这时用 `ui.push_id("xxx", |ui| { ... })` 或者给 `Window::new(...).id(...)` 显式指定 ID。

> 和 Dear ImGui 不同，egui 里**两个同名按钮是没问题的**（ID 自动生成不冲突）。ID 处理在 egui 里是个偶尔会遇到、但不算大的麻烦。

## 3.5 多 pass 即时模式

egui 默认一帧只跑一次 UI 代码（单 pass）。但有些场景需要再来一遍，可以用 `Context::request_discard` 请求丢弃当前 pass 并重跑。`Options::max_passes` 控制最多几次。

典型例子是 `Grid`：它第一次出现时不知道每列多宽，会猜错。`Grid` 在第一次出现时调用 `request_discard`，让 egui 再跑一遍用正确的列宽，用户就看不到错位了。

## 3.6 思维转换

从保留模式转过来，最大的思维转换是：

> **不要想着“创建控件 → 改控件 → 销毁控件”。每帧都是从零开始画一遍，你的数据就是控件的状态。**

习惯了之后你会发现 UI 代码变得非常短，而且没有“数据同步”的烦恼。
